What this project is

Notes · start here

The goal is to generate interfaces that are customizable, by generating them from a design space of UI patterns instead of straight from a prompt.

The goal

Generated interfaces should be customizable by default. The customization features come with the interface — they are not bolted on afterwards.

Right now a generated screen is frozen. You get what the model picked, and if you want it different you ask for a new one.

How

Don’t generate the interface directly. Generate a UI specification first, and build that spec out of a design space of patterns. This atlas is that design space.

  • A pattern is a known way to do a UI job — overview–detail, search, dashboard.
  • Each pattern has a design space: the dimensions you can vary.
  • Each dimension has variations. One variation per dimension is one interface.
  • Those picks are the spec, and the spec is what gets generated from.
  • Any dimension you leave open becomes a customization feature the user gets.

Why do it this way

Generating from a design space means the alternatives are already named. The interface knows what it could have been, so it can offer that choice to whoever is using it.

Generating from a prompt alone throws those alternatives away. Nothing is left to hand the user a control over.

The papers call this malleability. Same thing — how much of the interface the end user can change.

Where to start

Open the Atlas and click any card. The Configure block on a card is the whole idea in miniature: pick variations, and the spec below updates.

Twelve dimension families

Every dimension in every pattern is tagged with exactly one family. Content, Composition and Layout come from CHI ’25; the rest generalize Meridian and the study.

The ten-stage method

The design space of a pattern is simultaneously (a) its codebook for analysis, (b) its customization surface for end users, and (c) its generation target for GenUI. One artifact, three readings. Meridian made (b) and (c) literal for overview–detail by formalizing the space as a specification; the atlas extends that to every pattern.

1

Scope the pattern

Say what the pattern is made of, what it is also called, and what it is not.

ODI

Two views, overview and detail view (CHI §2.1), later three: overview, item view and detail view (UIST §2.1). Aliases master–detail and director–detail. Focus+context fenced off as a related but distinct pattern.

Atlas

Every entry names its components with one-line roles, its aliases, its neighbors, its level of abstraction and its home archetype.

The same three questions, specialized to each pattern’s own components. Generated from the entry, so they never drift from it.

3

Sample instances

Collect a diverse, representative set of real instances, with a unit of analysis defined so that one instance is one countable thing.

ODI

Four frames: Similarweb top 50 US sites; Semrush top 5 in each of 33 categories; 20 random WordPress showcase sites; 20 random Awwwards 2024 Sites of the Year. After de-duplication, 156 sites and 303 instances. Unit: one overview→detail relationship, so a page with two overviews counts twice (CHI §3.1.1).

Atlas

A written sampling frame and unit of analysis per pattern, ready to execute. Not executed.

4

Code to saturation

Turn instances into a codebook that more than one person applies the same way, and stop when new instances stop teaching anything.

ODI

Three authors independently coded 20 random instances and clustered their categories into an initial codebook. Two authors coded 20 more: 94.8% agreement (Cohen’s κ), then resolved differences. One author continued in random batches of 20, with both authors reviewing new dimensions after each batch. Stopped when three consecutive rounds added no dimension or variation; 120 instances coded in total (CHI §3.1.2).

Atlas

Each design space is a seed codebook. Saturation is recorded as not run for every pattern except overview–detail.

5

Construct the design space

Organize the codebook into dimensions, sub-dimensions and variations, each variation anchored to a real exemplar.

ODI

Content (attribute placement; visual, semantic and computational abstraction), Composition (relationships; recursion), Layout (overview–detail arrangement; overview layout; detail multiplicity). Figure 3.

Atlas

Dimensions → sub-dimensions → variations for every entry. Every dimension is tagged with one of twelve families, so the spaces can be compared with each other.

Automatable in this build

6

Audit existing customizability

Measure how much of the space end users can already reach, dimension by dimension.

ODI

13 of 156 sites (8.33%) offered any overview–detail customization: content 4 (2.56%), composition 0 (0%), layout 12 (7.69%). Craigslist offered the most, with five overview layouts and three overview–detail layouts; eBay let users toggle six attributes (CHI §3.3).

Atlas

A desk audit of customization features known in shipping products, plus an estimated 0–3 score. Measured shares exist only for overview–detail.

7

Design malleability techniques

Give end users a way to move along each dimension. The richest dimension gets a new technique; the others get familiar controls.

ODI

Content → Fluid Attributes: surface and hide attributes across views; sort and filter by any attribute; AI query, generation, reformatting and filling of missing values. Composition and layout → dropdown menus and tabbed overviews. Attributes invoke representations: select Price and Feedback Score for a scatter plot (CHI §4).

Atlas

Per-dimension techniques for every entry, one named signature technique, and AI-assisted variants flagged.

Automatable in this build

8

Formalize a specification

Express any point in the design space, and any customization, as a declarative document shared by designers, developers, end users and models.

ODI

Meridian: dataBinding (attributes with value, type, roles, groups, conditions and transforms) decoupled from views (overviews with type, itemView, shown and hidden attributes, bindingId; detailViews with openIn, openFrom, openBy; recursion by id), plus a malleability block per dimension (UIST §3).

Atlas

A shared grammar (binding, config, compose, malleability) and a per-pattern JSON Schema derived mechanically: each sub-dimension becomes a property whose values are its variations.

Automatable in this build

9

Demonstrate across domains and stakeholders

Show the space generalizes beyond the context it was found in, and that each stakeholder can act on it with familiar tools.

ODI

Five applications: shopping, hotels, email, live articles, mobile food delivery (CHI §5). End users: customization widgets, spec exchange, semantic zoom, direct manipulation mapped to spec moves, AI generation. Developers: a package reproducing AT&T, Marca and Merriam-Webster pages. Designers: a no-code builder with a Design Space grid and usage-driven defaults (UIST §4–6).

Atlas

Domain lists and techniques for every entry. Worked GenUI instance specs in genui/examples. The atlas document itself is a malleable overview–detail interface, a demonstration in its own right.

Automatable in this build

10

Compose real screens, and count what cannot be said

Test the grammar rather than the codebook. Freeze it, write eight real interfaces in it, make each screen declare the things it must be able to state, and treat every statement with no construct as a hole. Fill the holes, rewrite the screens that opened them, and go again.

ODI

Implicit in CHI '25: the five applications were written against one spec, and the spec's limitations section — imprecise arrangement, index conditions, no cross-item constraints — is exactly this stage's output, arrived at by building rather than by measuring.

Atlas

Five rounds of eight screens, forty in all, from a photo library to a cash machine. 275 claims, 29 holes, and five revisions that took the grammar from one relation to fourteen and from 5 constructs to 52; four holes are left open and named. Every spec validates against the published schema and resolves against the corpus, so an example cannot drift from the codebook it illustrates. Reported in Writing Screens.mrbl.

Automatable in this build

11

Evaluate and iterate

Watch people use the malleable pattern, then feed what they did, and failed to do, back into the space and the spec.

ODI

Design probes, N=12. Diverse configurations from identical starting points; hoarders vs minimalists; customizing at the start vs throughout; surface-then-sort and surface-then-filter; multiple overviews used to structure sub-tasks. Unmet: hover invocation and collection-level attributes (CHI §6–7). Spec limitations: imprecise arrangement, index-conditional attributes, a variable number of views (UIST §5.4).

Atlas

Hypothesized usage patterns and open questions per entry, phrased so that a probe study can test them.
